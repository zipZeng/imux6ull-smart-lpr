# 开发流程与排错

本文记录这个项目实际是怎么做出来的，以及联调时每一步卡住的原因和处理办法。当前的 MediaMTX 已经改到公网 `134.175.47.224`，上位机在 Linux 和 Windows 上各编一份。现在怎么开，以 [README.md](../README.md) 为准。下面从「这次联调的网络」起，记的是更早那次：MediaMTX 在 VMware 的 Ubuntu 里，靠 Windows 把 TCP 8554 转进去。

最初的设计是：开发板把摄像头已经压好的 MJPEG 原样推到 Ubuntu，两边在同一个局域网。这次在虚拟机和这块 UVC 摄像头上，那条路走不通。`board/stream.sh` 已经改成文末这条短命令：读取 YUYV，再编成 MJPEG。下面仍保留当时每一步的报错。

## 计划里的四步

1. 开发板用 FFmpeg 把 `/dev/video1` 推成 RTSP，Ubuntu 上的 MediaMTX 收这一路，路径名 `live`，端口 8554，传输只用 TCP。
2. Ubuntu 上的 Qt5 程序拉这路流，在窗口里显示。这一步不做车牌定位。
3. 把 Windows 工程 `License Plate Detector` 里的 `PlateDetector` 原样拷进客户端。拉流之后另开一个线程，大约每 200 毫秒拿最新一帧画框、裁出车牌小图。不做 OCR。
4. 收紧两端缓冲，并写明本机地址和公网地址怎么换。

代码按这四步落在仓库里。开发板只运行板上已有的 `ffmpeg`，不交叉编译 Qt 或 OpenCV，也不把整个仓库编译到板子上。

## 三台机器各放什么

| 位置 | 跑什么 | 不跑什么 |
| --- | --- | --- |
| i.MX6ULL（100ask） | 采集 `/dev/video1`，用 FFmpeg 推 RTSP | Qt、OpenCV、车牌定位 |
| Ubuntu 虚拟机 | `./mediamtx server/mediamtx.yml`，以及 `./client/build/lpr_client` | 板端脚本 |
| Windows 主机 | VMware，以及用来试看的 PotPlayer | 不参与定位算法 |

仓库根目录那份 764 行的 `mediamtx.yml` 是 MediaMTX 压缩包自带的官方默认配置。项目用的是 `server/mediamtx.yml`。启动命令是：

```bash
./mediamtx server/mediamtx.yml
```

MediaMTX 出现 `is publishing to path 'live'`，才表示有人正在推流。只有 `listener opened on :8554` 只说明端口在听。读者先连上、当时还没有推流时，日志是 `no stream is available on path 'live'`，播放器会显示「服务器已关闭或地址错误」。

## 这次联调的网络

Ubuntu 跑在 VMware NAT 里，开发板插在另一张网（手机热点）上。开发板访问不到虚拟机的 `192.168.30.128`。桥接网卡没有配上，最后用 Windows 上的端口转发把 8554 送进虚拟机。

这次实验里的地址：

```text
开发板 wlan1          192.168.172.229
        │  Wi-Fi，网关 192.168.172.2
        ▼
Windows 热点网卡      192.168.172.240
        │  VMware NAT 把本机 TCP 8554 转到虚拟机
        ▼
Ubuntu ens33          192.168.30.128
MediaMTX 监听         :8554
```

从开发板看到的转发来源是 `192.168.30.2`（NAT 网关），不是开发板自己的地址。日志里 `192.168.30.2` 是 Windows 上的 PotPlayer 被转进虚拟机，`192.168.172.229` 才是开发板在推流。

地址要这样填：

| 谁 | 地址 |
| --- | --- |
| 开发板推流 | `rtsp://192.168.172.240:8554/live` |
| 虚拟机里的上位机 | `rtsp://127.0.0.1:8554/live` |
| Windows 上的 PotPlayer | `rtsp://127.0.0.1:8554/live` |

开发板不要推到 `192.168.30.128`，虚拟机里的上位机也不要去连 Windows 的热点地址。换网络之后，只改开发板命令里的那个 Windows 地址，虚拟机里的 `127.0.0.1` 不用改。

## 摄像头实际能出的格式

`/dev/video0` 是芯片上的 pxp，不是 USB 摄像头。摄像头是 `/dev/video1`（USB 2.0 Camera），格式列表里既有 YUYV 也有 MJPEG。

用 `v4l2-ctl --stream-mmap` 实测：

- MJPEG，640×480 和 320×240，都没有任何帧。
- YUYV，640×480，大约 11 fps，画面正常。

所以不能用 `-c:v copy` 转发 MJPEG。板上的 FFmpeg 4.2（Lavf 58.29 / Lavc 58.54）要先读 YUYV，再编成 4:2:0 的 MJPEG，然后走 RTSP/TCP。i.MX6ULL 没有 H.264 硬编码器，这一步用软件 MJPEG，640×480、10 fps 时编码速度刚好在 `1x` 附近。

## 问题和解决办法

### 1. 开发板 ping 不通 Ubuntu 的 `192.168.30.128`

现象：`ping 192.168.30.128` 得到 `Network is unreachable`。`eth0` 没有网线，`eth1` 有链路但没有地址，DHCP 也没有回应。后来给 `eth1` 配了 `192.168.30.50`，仍然 100% 丢包。

原因：`192.168.30.0/24` 是 VMware NAT 里面的网段，只存在于 Windows 主机和虚拟机之间。开发板的网线没有接到这个网段。

处理：开发板改用 Wi-Fi `wlan1`，由热点分配 `192.168.172.229`。不要把设计文档里的示例地址 `192.168.1.20` 写到板子上。每次上电后的加载驱动和连接步骤见 [开发板连接手机热点.md](开发板连接手机热点.md)。

### 2. 虚拟机改桥接没有拿到地址

现象：在 Ubuntu 里重新向 `ens33` 要地址时命令停住，网卡上的 IPv4 消失。

原因：这台虚拟机的上网方式仍是 NAT。桥接没有成功，空等 DHCP 只会把原来的 NAT 地址弄掉。

处理：回到 NAT，确认 `ens33` 再次是 `192.168.30.128`。在 VMware 里把主机的 TCP 8554 转发到 `192.168.30.128:8554`。RTSP 使用 TCP 交织，不转发 UDP 端口。

### 3. 开发板能 ping 通 Windows，TCP 8554 仍是关闭的

现象：`ping 192.168.172.240` 正常。用 `/dev/tcp` 测 8554，结果是 `closed`。板上没有 `nc`。

原因：热点网络在 Windows 上经常是公用网络。端口转发已经在听，公用防火墙仍把入站 TCP 8554 丢掉。`ping` 通只说明 ICMP 通，不能说明 8554 通。

处理：入站规则放行 TCP 8554，专用和公用配置都要允许。然后再测：

```bash
timeout 5 sh -c 'echo >/dev/tcp/192.168.172.240/8554' && echo open || echo closed
```

这条板子上的 `sh` 支持 `/dev/tcp`。连通时先没有任何输出，加上 `echo open` 才会打印 `open`。

### 4. MediaMTX 没有任何新日志，PotPlayer 说服务器已关闭

现象：播放器标题是 `live`，提示「无法播放 / 服务器已关闭或地址错误」。MediaMTX 里只有启动时的监听日志，或者只有来自 `192.168.30.2` 的连接，并写着 `no stream is available on path 'live'`。

原因：这是读者连上了一个空路径。`192.168.30.2` 是 Windows 经 NAT 转进来的，不是开发板。开发板还没把流送进来。

处理：先在 Ubuntu 本机用测试画面证明 MediaMTX 本身能收流：

```bash
ffmpeg -hide_banner -loglevel info \
  -f lavfi -i testsrc=size=640x480:rate=15 \
  -c:v libx264 -pix_fmt yuv420p -g 15 -an \
  -f rtsp -rtsp_transport tcp \
  rtsp://127.0.0.1:8554/live
```

看到 `is publishing to path 'live'` 后，用 Ctrl+C 停掉测试画面，再查开发板。

### 5. FFmpeg 打开摄像头后没有像素格式

现象：即使没有别的进程占用 `/dev/video1`，下面这条命令也会报 `unspecified pixel format`，接着 `Cannot determine format of input stream 0:0 after EOF`。Ctrl+C 对应的是 signal 2。

```bash
ffmpeg -f v4l2 -input_format mjpeg -framerate 15 -video_size 640x480 \
  -probesize 5M -analyzeduration 5000000 \
  -i /dev/video1 -frames:v 3 -f null -
```

把 `-probesize` 和 `-analyzeduration` 加大没有用。当时的 `board/stream.sh` 在 `-i` 之前加了 `-fflags nobuffer`，探测更拿不到一张完整 JPEG，所以脚本看起来像停住，MediaMTX 也没有任何推流记录。这个参数后来已从脚本里去掉。

原因：驱动把 MJPEG 列在格式表里，但 `v4l2-ctl --stream-mmap` 实际等不到帧。问题在摄像头的 MJPEG 输出，不在 RTSP。

处理：改测 YUYV。640×480 的 YUYV 能连续打出 `<` 和 fps。MJPEG 这路放弃。

### 6. 编成 MJPEG 后 RTP 报 chroma block

现象：YUYV 已经读到，输出是 `mjpeg, yuvj422p`，然后每一帧都是：

```text
Only 1x1 chroma blocks are supported. Aborted!
```

原因：输入是 4:2:2。这块板子上的 FFmpeg 4.2 用 RTP 发送 JPEG 时，只接受 4:2:0。

处理：编码时加上 `-pix_fmt yuvj420p`。

### 7. MediaMTX 显示正在推流，大约 10 秒后超时

现象：日志先有 `is publishing to path 'live', 1 track (M-JPEG)`，板子上同时刷：

```text
RFC 2435 requires standard Huffman tables for jpeg
```

大约 10 秒后连接变成 `i/o timeout`，会话被拆掉。PotPlayer 若在这之后才打开，又会看到「服务器已关闭」。

原因：FFmpeg 4.2 的 MJPEG 编码器默认使用优化 Huffman 表。RFC 2435 的 RTP JPEG 只带量化表，不带 Huffman 表，播放端按标准表解码。表不一致时，RTP 包被丢掉，MediaMTX 等不到图像数据。

处理：加上 `-huffman default`。之后同一条连接能保持，PotPlayer 能看到画面。

随后还会出现 `RFC 2435 suggests two quantization tables, 1 provided`。这是提示编码器只给了一张量化表，这次画面已经正常，不用再改。

### 8. 画面通了，但 PotPlayer 比现场慢很多

现象：进度条类似 `00:00:05 / 00:00:33`。板子上的 `speed` 一直在 `1x` 左右，`drop=0`。

原因：右边的时间是播放器已经收到的长度，左边是它正在播的位置。它把直播先存了下来再播，所以会落在后面几十秒。这不是开发板越编越慢。

处理：把 PotPlayer 的进度条拖到最右边，跟上当前画面。看延迟时用虚拟机里的上位机。上位机只保留最新一帧（`CAP_PROP_BUFFERSIZE` 为 1），不会堆这几十秒。

FFmpeg 默认还有大约 0.7 秒的封装等待。推流命令里加上 `-muxdelay 0 -muxpreload 0` 可以去掉这一段。10 fps 本身还有大约 0.1 秒的帧间隔，板上软件编码再占大约一帧的时间。

## 当时虚拟机联调的启动顺序

下面这组地址只属于那次 VMware 端口转发。当前开发板应推到 `rtsp://134.175.47.224:8554/live`，上位机用同一个地址。

1. 确认 VMware 仍把主机 TCP 8554 转到 `192.168.30.128:8554`，Windows 防火墙仍放行这个端口。
2. 在 Ubuntu 上启动中转，窗口留着：

   ```bash
   ./mediamtx server/mediamtx.yml
   ```

3. 在开发板上推流。脚本里就是上面验证过的 YUYV 编码参数：

   ```bash
   ./stream.sh rtsp://192.168.172.240:8554/live
   ```

4. 等到 MediaMTX 出现 `is publishing to path 'live'`，并且超过 10 秒没有 `i/o timeout`。
5. 在虚拟机里打开上位机，地址用 `rtsp://127.0.0.1:8554/live`：

   ```bash
   ./client/build/lpr_client
   ```

   先点「开始」看画面，再点「开始定位」画框。Windows 上的 PotPlayer 也用 `rtsp://127.0.0.1:8554/live`，打开后把进度条拖到最右边。

`deprecated pixel format` 来自 YUYV 转到 JPEG 的色彩范围，可以忽略。
