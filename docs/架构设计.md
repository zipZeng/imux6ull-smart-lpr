# 架构设计

这份说明给第一次看本仓库的人。它解释系统为什么分成三截、每一截跑什么、每一截由哪些程序和函数完成，以及 Qt 窗口用了哪些组件。操作步骤以仓库根目录的 [README.md](../README.md) 为准。

## 要解决的问题

摄像头插在 i.MX6ULL 开发板上。人在 Linux 或 Windows 电脑前看实时画面，并在这台电脑上找出画面里的车牌位置。两边中间是一台只转发、不解码的云服务器。

开发板是单核 Cortex-A7，内存也小，上面没有 H.264 硬编码器。板上不做检测，也不编 H.264。这块摄像头的 MJPEG 模式没有帧，所以脚本读取 YUYV，再编成 4:2:0 的 MJPEG 推到网络上。

找车牌需要 OpenCV，窗口需要 Qt。这两件事放在上位机里。同一份 `client/` 在 Linux 上用 Qt 5 编译，在 Windows 上用 Qt 6 编译。

## 总体数据流

```text
USB UVC 摄像头
    │  插在开发板 USB Host，V4L2 设备节点 /dev/video1
    │  格式表里有 MJPEG 和 YUYV；MJPEG 没有帧，实际读取 YUYV
    ▼
board/stream.sh  →  ffmpeg 把 YUYV 编成 MJPEG
    │  RTSP，默认 TCP
    │  地址形如 rtsp://<服务器IP>:8554/live
    ▼
云服务器上的 MediaMTX（server/mediamtx.yml）
    │  公网 134.175.47.224:8554，内存里保住这一路，路径名 live
    ▼
Linux 或 Windows 上位机 client/
    ├─ CaptureThread   拉流、解码，每帧深拷贝后交给界面
    ├─ 主线程          QLabel 等比显示
    └─ DetectThread    仅在按下「开始定位」后，约每 200ms 拿最新一帧
            │
            ▼
       PlateDetector   传统图像处理，输出框和车牌小图
            │
            ▼
       主线程用红框画在画面上，右侧显示 ROI 和分数
```

开发板和上位机访问的是同一路 `live`，地址都是 `rtsp://134.175.47.224:8554/live`。MediaMTX 不保存录像，进程退出后画面就没了。更早一次把 MediaMTX 放在虚拟机里、靠 Windows 端口转发，地址见 [开发流程与排错.md](开发流程与排错.md)。

## 画面是怎么走的

编码在开发板上完成。云服务器上的 MediaMTX 只转发，不编码，也不找车牌。

1. **摄像头采到原始画面。** 摄像头插在开发板 USB Host 上，设备节点是 `/dev/video1`。实际送出的是 YUYV。YUYV 是未压缩的像素排列：每个点都有自己的亮度，相邻两个点共用一组颜色，平均每个像素 2 字节。640×480、大约 10 帧每秒时，带宽大约 50 Mbit/s。FFmpeg 里它叫 `yuyv422`，V4L2 里的格式名是 `YUYV`。它还不是 JPEG。格式表里也有 MJPEG，但这块摄像头的 MJPEG 模式一帧都没有。

2. **FFmpeg 在开发板上编码。** 仓库里的脚本不自己打开 `/dev/video1`，也没有自己的编码代码。`board/stream.sh` 把设备路径和参数交给板上已经装好的 FFmpeg。FFmpeg 用 V4L2 读出 YUYV，再用它自带的 MJPEG 编码器压成 4:2:0 的 JPEG。MJPEG 是一种视频：每一帧都是一张独立的 JPEG，帧和帧之间不互相参考。它和摄像头格式表里的 MJPEG 是同一种数据，这次由 FFmpeg 来压，不是摄像头来压。MediaMTX 和 Qt 程序都不编码；Qt 只把收到的 JPEG 解开来显示。这块单核板子在 10 帧时能编完。板上没有 H.264 硬编码器，所以不编 H.264。FFmpeg 4.2 用 RTP 发送 JPEG 时要求 4:2:0 和标准霍夫曼表，脚本里对应的参数是 `-pix_fmt yuvj420p` 和 `-huffman default`。

3. **用 RTSP over TCP 送到服务器。** 开发板把编好的 MJPEG 推到 `rtsp://134.175.47.224:8554/live`。RTSP 负责建立这一路会话，图像装在 RTP 里，再放进同一条 TCP 连接。端口是 8554，路径名 `live` 就是这一路画面的名字。服务器防火墙只放行了 TCP 8554，配置里也只接受 TCP。用 RTSP 是为了让开发板和上位机都只对着 MediaMTX，互不直连。Linux 上的 Qt 窗口、Windows 上的 Qt 窗口和 VLC 可以同时看这一路。

4. **服务器能拿到，是因为它正在听这个端口。** MediaMTX 在广州的云服务器上监听 8554，公网地址是 `134.175.47.224`。谁向路径 `live` 发布，谁就是来源。开发板从手机热点直接连这个公网地址，不再经过 Windows 端口转发。日志出现 `is publishing to path 'live'`，表示服务器已经收下这路 MJPEG。

5. **服务器收下之后只转发。** MediaMTX 把这路画面留在内存里，不解码，不定位，不写文件。上位机作为读者连接同一个 `rtsp://134.175.47.224:8554/live`，拿到同一路 MJPEG。Qt 程序把 JPEG 解成画面并显示。只有按下「开始定位」之后，才拿最新一帧找车牌。定位在打开窗口的那台电脑上，不在云服务器上。

## 三个节点

### 开发板

硬件关系：

- 摄像头是免驱 UVC，直接插 USB Host，不是板载的 OV5640 一类排线摄像头。
- 系统通过 V4L2 看到它，节点固定按 `/dev/video1` 使用。脚本发现这个节点不存在会退出并提示。
- 像素格式有 YUYV 和 MJPEG。格式表里的 MJPEG 用 `v4l2-ctl --stream-mmap` 等不到帧，所以 FFmpeg 读 YUYV。640×480 的 YUYV 大约 11 fps。脚本只检查这个节点在不在，读帧和编码都是 FFmpeg 做的。

`board/stream.sh` 的默认命令相当于：

```bash
ffmpeg -f v4l2 -input_format yuyv422 -framerate 10 -video_size 640x480 \
       -i /dev/video1 -an -c:v mjpeg -pix_fmt yuvj420p -huffman default -q:v 8 \
       -muxdelay 0 -muxpreload 0 -f rtsp -rtsp_transport tcp \
       rtsp://<服务器IP>:8554/live
```

YUYV 是 4:2:2。板上的 FFmpeg 4.2 用 RTP 发送 JPEG 时只接受 4:2:0，并且要求标准 Huffman 表，所以要写 `-pix_fmt yuvj420p` 和 `-huffman default`。地址用脚本的第一个参数；不写参数时读取环境变量 `RTSP_URL`。

封装时加了 `-muxdelay 0`、`-muxpreload 0`，少在发送前排队。分辨率和帧率可以用 `VIDEO_SIZE`、`VIDEO_FPS` 覆盖，默认 10 fps。

开发板上需要已经装好 `ffmpeg`。不需要本仓库的 Qt 工程，也不需要交叉编译。

### 流媒体服务器

MediaMTX 是一台现成的流媒体服务器，程序是仓库里的 `./mediamtx`，配置是 `server/mediamtx.yml`。它不拍画面，也不找车牌，只把推上来的那一路转给来看的人。

- RTSP 端口 `8554`
- 只接受 TCP（`rtspTransports: [tcp]`）
- 只有一个路径 `live`

它不关心推流的机器是谁。谁先往 `rtsp://<它正在听的地址>:8554/live` 推，谁就是这一路的来源；之后谁来拉，就拿到这一路。

当前部署里，MediaMTX 单独在云服务器 `134.175.47.224` 上。配置文件里不写 IP。开发板和两台上位机填的都是这个公网地址。程序放在 `~/imux6ull-smart-lpr/`，用 `nohup` 启动后，关掉 SSH 仍会继续听端口；服务器重启后要再启动一次。

没有人推流时，路径 `live` 是空的。这时上位机或 VLC 去拉，会得到 RTSP 404，MediaMTX 日志是 `no stream is available on path 'live'`。这不是地址写错，而是板上的 ffmpeg 还没连上。

开发板和上位机各跟 MediaMTX 建一条自己的 TCP，两边互不直连。图像和控制信息都走这条已经连上的 TCP，不再另开 UDP 端口，所以只转发 8554 就够了。

开发板推流时，FFmpeg 先连上 8554，再按顺序发三条 RTSP 命令：

1. **ANNOUNCE**：我要发布 `live`，里面是一路 MJPEG。
2. **SETUP**：这一路走当前这条 TCP。图像用通道 0，控制信息用通道 1。
3. **RECORD**：开始送画面。

MediaMTX 同意后，日志出现 `is publishing to path 'live'`。之后每张 JPEG 装在 RTP 里，继续写进这条 TCP。

上位机拉流时是另一条新的 TCP。点「开始」后程序连接 `134.175.47.224:8554`，命令顺序是：

1. **DESCRIBE**：请告诉我 `live` 里有什么。有人正在推，就返回「一路 MJPEG」；还没有推流，就返回 404。
2. **SETUP**：同样约定走这条 TCP。
3. **PLAY**：开始收画面。

MediaMTX 把开发板那条连接里收到的 JPEG，写进上位机这条连接。开发板断开时，阅读也会跟着结束。

### 上位机

Linux 和 Windows 各跑一份从 `client/` 编出来的程序，界面和拉流代码相同。Linux 用 Qt 5，产物是 `client/build/lpr_client`。Windows 用 Qt 6，产物是 `client\build\Release\lpr_client.exe`。两边都是 x86_64 程序，不能拷到开发板上跑，也不能把 Linux 的 `client/build` 拿去在 Windows 上继续编译。窗口在 `MainWindow` 的构造函数里用布局搭出来，没有单独的界面设计文件。拉流前设置 `OPENCV_FFMPEG_CAPTURE_OPTIONS`，让 OpenCV 的 FFmpeg 走 TCP；Linux 用 `setenv`，Windows 用 `_putenv_s`。

窗口默认不超过 1120×720，并且不超过当前屏幕可用区域的八成。标题是「远程车牌定位」。上面一排是地址框和按钮，地址默认 `rtsp://134.175.47.224:8554/live`。下面一行是状态文字。中间左边是 `videoLabel_`，深色底，没连上时显示「尚未连接」；右边是定位状态、车牌小图、宽高比和得分。拉流之前「开始定位」是灰的，拉流之后「选择图片」是灰的。

播放不用 Qt 自带的播放器。点「开始」后，`onStart()` 新建一个 `CaptureThread`。这个线程不碰控件。它用 OpenCV 的 FFmpeg 打开地址栏里的 RTSP，强制走 TCP，缓冲只留 1 帧，然后循环读帧。读到的图可能被下一次读取盖掉，所以发出去之前先 `clone()`。信号用队列交回主线程。

主线程的 `onFrame()` 收到 OpenCV 的 BGR 图，转成 RGB 的 `QImage` 并 `copy()`，存进 `baseImage_`。第一帧到达后，状态变成「正在播放 640×480」。`refreshView()` 拿这张图的副本，定位开着就用 `QPainter` 在副本上画红框，再按标签当前大小缩放，保持宽高比，放进左边的 `QLabel`。窗口大小变化时会再画一次。点「停止」只是让拉流线程自己退出。

界面和算法分开：

| 部分 | 文件 | 职责 |
| --- | --- | --- |
| 拉流 | `CaptureThread` | 用 `cv::VideoCapture` 和 FFmpeg 后端打开 RTSP。每帧 `clone()` 后再发给界面，避免下一帧覆盖还在显示的缓冲 |
| 显示 | `MainWindow` | 把 OpenCV 的 BGR 图转成 `QImage` 并 `copy()`，在 `QLabel` 里按比例缩放 |
| 定位 | `DetectThread` + `PlateDetector` | 只保留最新一帧。定位忙时丢掉中间帧，并且大约 200 毫秒才跑一次 |
| 画框 | `MainWindow` | 用 `QPainter` 画红框。算法内部的绿框不显示 |

跨线程用 Qt 的队列信号。定位线程不碰控件。

`PlateDetector.h` 只包含 OpenCV，不能包含 Qt。这样同一份算法既能被界面调用，也能脱离窗口做图片测试。`client/src/PlateDetector.cpp` 是从 `License Plate Detector/src/` 拷来的，阈值仍在该文件顶部的 `cfg`。

## 各节点由什么完成

开发板和云服务器这两截没有本仓库自己的 C 或 C++ 函数。开发板是 shell 脚本加上板上的 `ffmpeg` 可执行文件。云服务器是现成的 `mediamtx` 可执行文件，读 `server/mediamtx.yml`。只有上位机的拉流、显示和定位是这个仓库里的函数。

### 开发板

`board/stream.sh` 自己做的事是检查参数和设备，然后用 `exec` 把进程换成 `ffmpeg`。脚本里没有图像处理函数。

| 脚本里的判断 | 作用 |
| --- | --- |
| `VIDEO_DEVICE`、`VIDEO_SIZE`、`VIDEO_FPS`、`RTSP_TRANSPORT`、`RTSP_URL` | 给出设备、分辨率、帧率、传输方式和地址。第一个命令行参数优先于 `RTSP_URL` |
| `[[ ! -e "${DEVICE}" ]]` | 设备节点不存在就退出 |
| `[[ ! -r "${DEVICE}" ]]` | 节点在但读不了就退出，并提示把用户加入 `video` 组 |
| `command -v ffmpeg` | 板上没有 `ffmpeg` 就退出 |
| `exec ffmpeg ...` | 用 FFmpeg 替换当前 shell，后面不再回到脚本 |

真正打开摄像头、编码和推流的是这条 `ffmpeg` 命令里的选项，不是自写函数：

| 选项 | 作用 |
| --- | --- |
| `-f v4l2 -input_format yuyv422 -framerate -video_size -i` | 用 V4L2 打开 `/dev/video1`，读取 YUYV |
| `-c:v mjpeg -pix_fmt yuvj420p -huffman default -q:v 8` | 编成 4:2:0、标准霍夫曼表的 MJPEG |
| `-muxdelay 0 -muxpreload 0` | 少在发送前排队 |
| `-f rtsp -rtsp_transport tcp` | 按 RTSP over TCP 推到地址栏里的 URL |

### 云服务器

仓库里没有 MediaMTX 的源码，这一截也没有自己的函数。`server/mediamtx.yml` 只写了四项：`rtsp: true`、`rtspAddress: :8554`、`rtspTransports: [tcp]`、`paths.live`。进程启动后由 MediaMTX 自己听端口、收 RTSP、把 JPEG 从发布者那条 TCP 抄到读者那条 TCP。

开发板那条连接上的 RTSP 方法是 ANNOUNCE、SETUP、RECORD。上位机那条连接上的是 DESCRIBE、SETUP、PLAY。这些方法由 FFmpeg 和 MediaMTX 实现，上位机代码里不手写 RTSP 报文。

### 上位机

入口在 `client/src/main.cpp` 的 `main()`。它创建 `QApplication`，构造 `MainWindow`，调用 `show()`，再进入 `app.exec()` 事件循环。Qt 5 在这之前调用 `QApplication::setAttribute(Qt::AA_EnableHighDpiScaling)`。Qt 6 没有这个属性，高分屏由库自己处理。

拉流、定位、显示分成三类函数：

| 函数 | 所在线程 | 做的事 |
| --- | --- | --- |
| `CaptureThread::run()` | 拉流线程 | `cv::VideoCapture::open(url, cv::CAP_FFMPEG)`，`cap.set(CAP_PROP_BUFFERSIZE, 1)`，循环 `cap.read()`，每帧 `clone()` 后 `emit frameReady` |
| `CaptureThread::requestStop()` | 主线程调用 | 把 `stop_` 设为 true，让 `run()` 里的循环退出，再 `cap.release()` |
| `MainWindow::onFrame()` | 主线程 | `matToQImage()`，存进 `baseImage_`，若定位线程已启动则 `DetectThread::submit()`，然后 `refreshView()` |
| `DetectThread::submit()` | 主线程调用 | `QMutexLocker` 锁住后，用新帧盖掉 `pending_`，`cond_.wakeOne()` |
| `DetectThread::run()` | 定位线程 | `cond_.wait()` 等到有帧，大约每 200 毫秒取最新一帧，调用 `PlateDetector::locatePlate()`，再 `emit detectionReady` |
| `PlateDetector::locatePlate()` | 定位线程，或选图时的主线程 | 依次调用下面表格里的算法函数 |
| `MainWindow::onDetection()` | 主线程 | 调用 `applyDetection()`，把框和 ROI 交给界面 |
| `MainWindow::refreshView()` | 主线程 | `paintPlates()` 画红框，`paintLabel()` 把图放进两个 `QLabel` |

`locatePlate()` 内部按这个顺序调用本文件里的函数：

| 函数 | 作用 |
| --- | --- |
| `preProcess()` | 灰度、高斯、垂直 Sobel、二值化、开运算和闭运算，得到边缘图、二值图和掩码 |
| `getPlateContours()` | 在掩码上找外轮廓，按面积、宽高比、矩形度、倾斜和边缘强度留下正对的框 |
| `keepPaintedPlates()` | 在候选框里统计蓝、黄像素，去掉车标和镀铬字 |
| `findTiltedColorPlates()` | 用颜色掩码找侧拍时的旋转矩形 |
| `findTiltedEdgePlates()` | 夜间或蓝车身时，用字符边缘再找旋转矩形 |
| `suppressOverlap()` | 重叠的框只留得分高的，最多 3 个 |
| `drawAndCropPlate()` | 裁出车牌小图。界面上的红框不用这里画的绿框 |

### 拉流线程交给界面

`CaptureThread` 和 `DetectThread` 都继承 `QThread`。它们不持有 `QLabel` 或 `QPushButton`。跨线程用信号，连接类型是 `Qt::QueuedConnection`，槽在主线程执行。

`CaptureThread` 的构造函数调用 `qRegisterMetaType<cv::Mat>()`，`DetectThread` 的构造函数调用 `qRegisterMetaType<LocateResult>()`。排队传递这两类参数时，Qt 需要这份注册。

| 信号 | 槽 | 何时发出 |
| --- | --- | --- |
| `CaptureThread::frameReady(cv::Mat)` | `onFrame()` | `cap.read()` 读到一帧并 `clone()` 之后 |
| `CaptureThread::errorOccurred(QString)` | `onCaptureError()` | `cap.open()` 失败，或连续三次没有读到帧 |
| `QThread::finished` | `onCaptureFinished()` | `run()` 返回 |
| `DetectThread::detectionReady(LocateResult)` | `onDetection()` | `locatePlate()` 返回 |
| `DetectThread::errorOccurred(QString)` | `onDetectError()` | `locatePlate()` 抛出 `cv::Exception` |
| `QThread::finished` | `onDetectFinished()` | 定位线程退出 |

`DetectThread` 用 `QMutex`、`QWaitCondition` 和 `QMutexLocker` 保护 `pending_`。`submit()` 只保留最新一帧。定位还在算时，后来的帧直接盖掉还没算的那一帧。

### 显示用到的函数

`onFrame()` 先调用 `matToQImage()`。彩色帧走 `cv::cvtColor(..., cv::COLOR_BGR2RGB)`，再用 `QImage` 的构造函数包住这块内存，并立刻 `copy()`。灰度的边缘图和掩码用 `QImage::Format_Grayscale8`，同样 `copy()`。`copy()` 是因为 `QImage` 不能一直指着下一帧就会被覆盖的 OpenCV 缓冲。

`refreshView()` 复制 `baseImage_`。需要画框时，`paintPlates()` 在副本上创建 `QPainter`，`setRenderHint(QPainter::Antialiasing)`，`setPen(QPen(...))`。有四个角点时 `drawPolygon(QPolygon)`，否则 `drawRect()`。算法内部的绿框不画到界面上。

`paintLabel()` 把这张图放进 `QLabel`：`QPixmap::fromImage()`，再 `scaled(label->size(), Qt::KeepAspectRatio, Qt::SmoothTransformation)`，最后 `setPixmap()`。没有图时 `setPixmap(QPixmap())` 并 `setText()` 显示占位文字。

窗口尺寸变化时，`resizeEvent()` 和 `showEvent()` 再调用一次 `refreshView()`，所以画面跟着标签的当前大小缩放，不把 640×480 固定死。

`setStreaming()` 只改按钮和地址框：`setEnabled()`、`setReadOnly()`。拉流时「开始」和「选择图片」变灰，「停止」和「开始定位」可点。

### 选图和调试窗口

`onSelectImage()` 调用 `QFileDialog::getOpenFileName()`。起始目录来自 `sampleDirectory()`，它用 `QDir` 依次找 `License Plate Detector/images`。读图用 `cv::imread()`，再在主线程直接调用 `locatePlate()`，因为这时没有视频线程。打不开文件、空图或 OpenCV 异常时调用 `QMessageBox::warning()` 或 `QMessageBox::critical()`。

`onViewDebug()` 创建临时的 `QDialog`，里面一个 `QHBoxLayout`，三列各是一个 `QVBoxLayout`：标题 `QLabel` 加一张图。三张图是边缘、二值图和闭运算掩码，用 `QPixmap::fromImage().scaled(460, 420, Qt::KeepAspectRatio, Qt::SmoothTransformation)`。对话框用 `dialog.exec()` 一直显示到关掉。还没有中间图时调用 `QMessageBox::information()`。

线程结束时不在槽函数里直接 `delete`。`onCaptureFinished()` 和 `onDetectFinished()` 调用 `deleteLater()`，等主线程事件循环把对象删掉。析构函数里则先 `disconnect()`，再 `requestStop()` 和 `QThread::wait()`，避免窗口关掉时线程还在发信号。

## 定位算法在整条链路里的位置

算法不读摄像头，也不知道 RTSP。它的入口是 `locatePlate(一张 BGR 图)`，输出是：

- 零到三张车牌候选（位置、四个角、宽高比、得分、倾斜角）
- 裁好或透视拉正的车牌小图
- 边缘图、二值图、闭运算掩码，给定调试按钮看

它同时试几条路：正对时的字符竖边缘、蓝/黄底色块、侧拍时的旋转矩形。规则针对单行蓝牌和黄牌。新能源绿牌、双层黄牌、夜间强反光不保证能框住。640×480 里特别小的牌，也可能需要改 `cfg`，改完要用 `License Plate Detector/images/` 里的样图再看一遍。

上位机的「选择图片」就是把一张本地图送进同一个 `locatePlate()`。样图能出框，只说明算法移植没变；实时视频还要等开发板真的把流推上来。

## 网络是这条链路的前提

推流地址里的 IP 不是写在 `mediamtx.yml` 里的。当前是云服务器的公网地址 `134.175.47.224`。开发板先按 [开发板连接手机热点.md](开发板连接手机热点.md) 拿到地址，再执行 `stream.sh`。MediaMTX 打出正在向 `live` 发布，最后才打开上位机。

开发板 `ping` 这个公网地址时如果是 `Network is unreachable`，说明热点还没连上，ffmpeg 还没开始工作。更早一次虚拟机 NAT 加 Windows 端口转发的地址见 [开发流程与排错.md](开发流程与排错.md)。

## 刻意不做的事

- 不在开发板上跑车牌定位。板上把 YUYV 编成 MJPEG，不把整帧转成 RGB，也不编 H.264。i.MX6ULL 没有可用的 H.264 硬编码器。
- 第一版不做车牌字符识别。字符识别如果要加，输入应是现在已经裁好的 ROI，而不是整帧画面。
- 不改 `License Plate Detector` 里的算法和它的 Visual Studio 路径。上位机用的是拷进 `client/src/` 的那一份。Windows 上新编的 `lpr_client.exe` 是这份额外的查看和定位程序，不是那个选图工程。
